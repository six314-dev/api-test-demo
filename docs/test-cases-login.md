# 登录功能 · 测试用例设计

> 需求假设（真实项目请以 PRD 为准）：
> - 用户通过「用户名 + 密码」登录
> - 用户名：4—20 位，字母/数字/下划线
> - 密码：6—20 位，区分大小写
> - 连续 5 次密码错误，账号锁定 15 分钟
> - 登录成功返回 token，失败返回错误提示

## 一、设计思路（先想清楚，再写用例）

登录是一个「输入两个字段、判断一个结果」的功能，最适合用**等价类划分 + 边界值分析**来设计。

**用户名/密码的有效等价类**：格式合法、长度在 6—20 之间
**无效等价类**：为空、长度不足、长度超限、含非法字符、格式正确但不存在

**边界值**：密码长度 5 / 6 / 20 / 21，这四个点最容易出问题

一个常见的误区是「只测对的、只测错的」。真正有价值的用例，是那些**能暴露开发没想到的情况**的用例。

|---|---|---|---|---|---|---|---|
| TC-LOGIN-001 | 正确的用户名和密码登录成功 | 正向 | P0 | 账号 `testuser` 已注册且状态正常 | 用户名 `testuser`，密码 `Test@123456` | 1. 打开登录页<br>2. 输入用户名、密码<br>3. 点击登录 | 1. 提示登录成功<br>2. 返回 token（或写入 Cookie）<br>3. 跳转到首页 |

## 三、每条用例为什么这么设计

**TC-LOGIN-001 正向主流程**
不是「能登录就行」，重点验证三件事：成功提示、**token 是否真的返回**、是否跳转。很多 bug 出现在「提示成功了但其实没拿到 token」。

**TC-LOGIN-002 密码错误**
关键在**提示语**。安全要求高的系统应该统一提示「用户名或密码错误」，而不是「密码错误」——后者会泄露「这个用户名是存在的」，方便攻击者枚举账号。测试时要能识别出这是安全问题，而不是文案问题。

**TC-LOGIN-003 / 004 必填校验**
除了看提示语，还要看**是否发起了网络请求**。好的实现是前端就拦住了；如果空值也发到后端，说明前端校验缺失，会白白消耗服务器资源。用浏览器 F12 的 Network 面板可以验证这一点。

**TC-LOGIN-005 边界值**
密码 5 位是最容易被漏掉的点。特别要区分两种失败：**格式不合法**（提示「长度不符」）和**凭证错误**（提示「密码错误」）。如果 5 位密码返回的是「密码错误」，说明后端把格式校验和认证混在一起了，这是设计缺陷。

## 五、写用例时容易犯的错

1. **步骤写成「测试登录功能」** —— 步骤必须具体到「输入什么、点哪里」，别人照着能复现。
2. **预期结果写「登录失败」** —— 要写清楚：提示什么文案、是否跳转、是否返回 token、输入框是否清空。
3. **只写正向用例** —— 面试官更关心你怎么设计异常场景。
4. **没有优先级** —— 时间不够时先跑 P0，这是测试的基本功。
5. **把多条验证点塞进一条用例** —— 一条用例只验证一个点，失败了才知道是哪里出问题。

## 六、下一步

这 5 条是**手工用例**，是接口自动化的设计蓝本。
等进入接口测试阶段，TC-LOGIN-001 会变成一条 pytest 用例：

```python
def test_login_success():
    resp = requests.post(LOGIN_URL, json={"username": "testuser", "password": "Test@123456"})
    assert resp.status_code == 200
    assert resp.json()["token"]           # 断言 token 存在
```

先会设计，再会编码 —— 顺序反了，写出来的自动化测试只是「把手工点点点换成了代码点点点」。
